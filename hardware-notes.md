# Steam Deck hardware notes

Collected from the Linux system visible to this workspace on 2026-10-30. These identify the target; they are not a macOS framebuffer configuration.

## GPU

- System: Valve Steam Deck, board/product `Jupiter`, BIOS `F7A0131`.
- PCI function: `0000:04:00.0`, AMD Van Gogh / AMD Custom GPU 0405.
- PCI IDs: vendor/device `1002:163F`, subsystem `1002:0123`, revision `AE`.
- ACPI path reported by Linux: `\\_SB_.PCI0.GP17.VGA_`.
- Linux driver: `amdgpu`; kernel `6.18.44-1-lts`.
- VBIOS identifier: `113-AMDAerithJ-005`, fetched by Linux from the ACPI `VFCT` table.
- The local `VFCT.bin` copy is 45,188 bytes. Its matching `1002:163F` entry contains a 45,056-byte ATOMBIOS ROM (`VANGOGH`, `JupiterGener`); the extracted ROM's byte checksum is zero modulo 256.
- Linux-reported memory: 4096 MiB VRAM, 128-bit LPDDR5; the driver also creates a GTT aperture.
- Linux-reported display engine: DCN 3.0.1. Other detected blocks include GFX 10.x, SDMA 5.2, VCN 3.0, and JPEG 3.0.
- The boot log reports IP discovery for common, GMC 10, IH 5, PSP 11, SMU 11, display manager, GFX 10, SDMA 5.2, VCN 3, and JPEG 3. Linux loads the ATOM VBIOS through VFCT, initializes SMU and DMUB, then registers the amdgpu DRM device.
- The detailed boot log pins down the display bring-up baseline: Linux loads DMUB through PSP (`0x03000010`), initializes SMU successfully, starts Display Core `3.2.351` on DCN `3.0.1`, and reports DMUB hardware at the same version. It reserves a 10 MiB PSP TMR at `0xF4FE000000`. These are reference observations from Linux; the TMR address is runtime-assigned and must not be reused as a macOS constant.
- `modetest.txt` records the internal panel on CRTC 80 at 800x1280@60 and its plane rotation capability. The later live debugfs capture is authoritative for current state: CRTC 80 drives plane 59 with an AR24 1280x800 source, pitch 5120, 800x1280 destination, and DRM `rotation=8` (270 degrees); DCN HUBP reports `rot=3`. The connector's `Right Side Up` orientation agrees. The DRM mode has positive horizontal and vertical sync and a 69.270 MHz pixel clock; the kext's detailed timing now reports those polarities and a digital single-link signal. The live HUBP line also reports DCC enabled and swizzle mode `0x1b`, while DRM reports an AMD GFX10 RB+ tiled modifier. These memory-layout fields and the BO address are runtime allocation details; don't copy them as static kext values. Linux DCN 2.x shared HUBP code maps 270 degrees to `DCSURF_SURFACE_CONFIG.ROTATION_ANGLE=3`; using that register update alone is insufficient because the surface, tiling/DCC, timing, and pipe state must also be valid. Apple's `IODisplayScalerInformation` expects maximum source dimensions before rotation, so the kext now advertises 1280 horizontal by 800 vertical for the landscape source buffer and a 270-degree detailed timing transform.
- I ran RedNavi's read-only `tools/linux_ip_discovery.py 0x163f` against this Deck's live sysfs table. It confirms GC `10.3.1`, SDMA `5.2.1`, MP0/MP1 `11.5.0`, DMU `3.0.1`, VCN/UVD `3.0.2`, MMHUB `2.3.0`, NBIF `7.2.0`, and UMC `10.0.0` across four instances. Key discovery bases are GC `0x1260 / 0xA000 / 0x2402C00`, MP0/MP1 `0x16000 / 0x243FC00 / 0xDC0000 / 0xE00000 / 0xE40000`, and DMU `0x12 / 0xC0 / 0x34C0 / 0x9000 / 0x2403C00`. The same values are visible in amdgpu's sysfs `ip_discovery`; offsets are not PCI BAR addresses and must be resolved through the device's IP/register mapping.
- RedNavi is a Navi 32 implementation: its tested card has GC 11.0.3, PSP/SMU 13.0.10, SDMA 6.0.3, and DCN 3.2.0. The Deck is Van Gogh with GC 10.3.1, PSP/SMU 11.5.0, SDMA 5.2.1, and DCN 3.0.1. The useful carryover is its staged discovery and Linux capture workflow; its firmware images, register offsets, display replay, and boot arguments are not transferable to Van Gogh.
- `nullarc-main` is a more relevant APU workflow comparison than RedNavi, but it targets Phoenix/Hawk Point Radeon 780M (`1002:1900`, `gfx1103`, GC 11.0.1, PSP/SMU 13.0.4, SDMA 6.0.1, DCN 3.1.4). The Deck is Van Gogh (`1002:163F`, `gfx1033`, GC 10.3.1, PSP/SMU 11.5.0, SDMA 5.2.1, DCN 3.0.1). Its per-block state machines, firmware types/sequences, MMIO definitions, memory assumptions, and DCN implementation therefore cannot be reused as Van Gogh hardware support.
- Linux's Van Gogh PSP path is distinct from Navi/Phoenix: MP0 `11.5.0` requests `vangogh_asd.bin` and `vangogh_toc.bin` (not the sOS/TA pair used on PSP 11.0 variants). The host has those compressed payloads, along with Van Gogh GFX/SDMA/VCN and DMUB firmware, under `/lib/firmware/amdgpu`. Linux's generic SMU 11 loader separately requests the MP1-version-named `.bin` image; the expected Van Gogh SMU payload is not present in this host's firmware directory, so that input still needs to be located/captured before a complete firmware inventory can be claimed. The captured Linux log says DMUB is loaded through PSP (`0x03000010`), followed by SMU and DMUB initialization. A macOS port therefore needs PSP command transport, protected VRAM allocation/TMR management, and validated firmware headers before SMU or DCN can start. The current IFWI-ready read is only observation; it does not mean this kext has initialized PSP. The new standalone parser can check ASD and TOC common-header bounds when both images are supplied as provider OSData properties, but deliberately does not submit them. Do not reuse RedNavi's PSP/SMU sequence or write firmware through guessed MMIO offsets.
- The reusable contribution from nullarc is its engineering shape: separate bounds-checked IP discovery and memory planning from hardware access; model PSP, SMU, SDMA, and GFX bring-up as explicit stages; and validate pure calculations with host tests before touching hardware. For Van Gogh, build a parallel implementation from Van Gogh Linux `amdgpu`/DCN301 sources and this Deck's captures, retaining runtime PCI/BAR discovery and a disabled-by-default bring-up path. Do not copy its canned Phoenix values (including `GB_ADDR_CONFIG`, VRAM layout, firmware IDs, or register addresses). Nullarc's own license table permits its bring-up code under MIT or GPL-2.0-only; its `phxaccel` and `nmplugin` are separately PolyForm Noncommercial, so check file-level licensing before adapting any code.
- The matching upstream Linux display implementation is `drivers/gpu/drm/amd/display/dc/resource/dcn301/dcn301_resource.c`, together with `vangogh_ip_offset.h`, DCN 3.0.1 register headers, and shared `dcn30` components. That resource pool explicitly marks DCN301 as an APU, enables DMUB support, and constructs the AUX engines, panel control, link encoders, timing generators, and planes. Its fixed resource table has four timing generators/planes and four stream encoders/DDC engines; actual connector routing still comes from this Deck's VBIOS and ACPI data. This source is MIT-licensed, but it depends on a large DC framework, so it is a source map for a port rather than a drop-in kext implementation.
- The display-register mapping uses DCN discovery HWID 271. Linux's `vangogh_ip_offset.h` gives `DCN_BASE` segment 2 as dword base `0x34C0`, matching that live table entry. The DCN 3.0.1 register header puts `HUBP0..3_DCSURF_SURFACE_CONFIG` at dword offsets `0x05E5`, `0x06C1`, `0x079D`, and `0x0879`, all with base-index 2; resolved BAR5 byte offsets are therefore `0xEA94`, `0xEE04`, `0xF174`, and `0xF4E4`. Their rotation field is bits 8–9 (`mask 0x300`), where 270 degrees is value 3. The kext reads those surface configs and, for a populated format, also captures tiling mode, viewport dimensions, pitch, primary address registers, DCC control, HUBP VMID, and HUBP control. It publishes raw state in `VanGoghDCN301,HUBP-surface-state`, rotation masks/values, and a linear/uncompressed layout-candidate mask. Address register values are GPU virtual addresses, not CPU physical addresses; a matching GPUVM mapping/page table is required before a new system allocation can be scanned out.
- Rotation defaults to 270 degrees on the detected active panel HUBP mask. A single-HUBP request can override it with PCI-provider property `VanGoghDriver,program-hubp-rotation`, encoded as `(HUBP index << 8) | angle`; angle 3 means 270 degrees, so `0x0003` selects HUBP0 and `0x0303` selects HUBP3. Split-HUBP requests use `VanGoghDriver,program-hubp-rotation-mask` and `VanGoghDriver,program-hubp-rotation-angle`; explicit mask `0` disables writes. Each target must have a readable populated surface; the driver changes only bits 8–9, verifies the write, rolls back on mismatch, and restores the previous full surface-config value on detach only if the register still matches what it wrote. It does not set up clocks, timing, link, or framebuffer memory.
- The driver resolves the internal panel path by matching captured eDP OTG totals, reading that OTG's ODM source selection to find its OPP input(s), following their non-disabled MPCC inputs, then mapping DPP IDs to HUBP IDs using DCN301's one-to-one resource pool. On the Linux capture this resolves to HUBP0 and HUBP3 (`mask 0x9`). The detected mask is used by default, and each requested surface config is verified after write and conditionally restored on detach.
- DCN301 OTG timing readback uses the AMD `dcn_3_0_1_offset.h` map (OTG0 base `0x1B2A`, instance stride `0x80` dwords, discovery segment 2) and captures H/V totals, blanking, sync, sync polarity, and OTG enable. This is read-only and establishes live pipe state before any mode-set work.
- Pipe topology readback now captures ODM source-select registers in DCN segment 2 and MPCC top/bottom/OPP/control registers in segment 3. These snapshots are needed to associate a HUBP with the internal eDP output before replacing a plane; they remain read-only.
- HUBP readback also publishes the four VMID nibbles as `VanGoghDCN301,HUBP-VMID-values` and raw control words as `VanGoghDCN301,HUBP-control-values`, making it possible to inspect the active address-translation context without decoding the complete surface-state blob.
- The driver owns a zeroed, prepared, physically contiguous 1280x800 ARGB allocation (5120-byte pitch) and publishes its physical range and geometry. It deliberately does not mark the framebuffer ready: no HUBP surface address/format/pitch programming, display clock setup, eDP stream setup, or complete pipe verification exists yet. The descriptor remains prepared for device access while owned and is completed/released with the PCI service.
- XNU `IODMACommand` creates PCI I/O bus addresses through an I/O mapper; AMD DCN301 consumes a GPU virtual address selected by HUBP VMID. They are different address spaces. The current kext exposes only the allocation's CPU physical address and explicitly reports `gpuvm-scanout-ready=false`; it must not feed that physical address directly to HUBP.
- Van Gogh's Linux path uses `gmc_v10_0` with GFXHUB 2.1 (GC 10.3.1) and MMHUB 2.3 (MMHUB 2.3.0). GART enable allocates/programs VMID0's page directory, sets the page-table range and system aperture/default page, initializes TLB/cache, enables system-domain mappings, disables identity aperture, sets VMID policy, and configures invalidation. A working scanout mapping therefore depends on GMC/VM initialization, not a HUBP-only physical-address write.
- The kext now reads MMHUB HWID 34, base segment 1, VMID0 context control, page-table base/range, and system aperture registers into `VanGoghGMC,VMID0-state`. This records existing firmware/OS setup without changing GMC state; the scanout path remains marked unavailable until an owned GPUVM mapping exists.
- Linux DCN301's actual plane path confirms that rotation is one part of a larger state transition. `hubp3_program_surface_config` programs DCC state, tiling, size/pitch, rotation, and pixel format; `dcn20_update_plane_addr` installs the address separately. The display HW sequencer then coordinates front-end pipe/plane setup, timing generators, clocks, stream encoders, eDP link training/unblank, and backlight. The live Deck plane is DCC-compressed and tiled, so its layout cannot be relabeled as a linear macOS surface. Until the kext has a valid VRAM allocation and the DCN301 plane/pipe/link sequence, a single rotation-register write would not produce a usable rotated framebuffer and could corrupt the active display.
- The log reports 4 GiB VRAM at `0xF400000000`, 1 GiB GART, a 1024 MiB GART aperture, and 5898 MiB GTT. These are Linux runtime allocations and addresses, not safe macOS values to copy directly.
- `lspci` reports BAR0 as a 256 MiB 64-bit prefetchable memory region, BAR2 as a 2 MiB 64-bit prefetchable region, BAR4 as 256 I/O ports, and BAR5 as a 512 KiB non-prefetchable memory region. BAR5 begins at `0x80300000`, matching the amdgpu log's register-MMIO base; the driver reports a 512 KiB MMIO size. Linux assigns these addresses, so macOS must discover/map its own resources rather than hard-code them.
- PCI capabilities include MSI-X with four vectors (table and PBA in BAR5), power management, ATS, PRI, and PASID. The `lspci` report says the endpoint link is 8 GT/s x16; the kernel is bound to `amdgpu`.
- Linux applies a panel backlight quirk (`min_brightness: 0`) and uses a custom brightness curve. This supports the need to investigate brightness behavior separately from basic eDP mode setting.
- Two `Failed to add display topology, DTM TA is not initialized` messages appear, but amdgpu continues to initialize and drives both displays. They are not evidence that the DRM display path failed.

## Linux driver source trace

The running host reports Linux `6.18.44-1-lts`; `amdgpu` is loaded for `0000:04:00.0`. Its installed module is compressed (`amdgpu.ko.zst`, module `srcversion` `B060269F803B47449E96381`), and the installed kernel build tree has headers/Kconfig but not the AMD driver source. I inspected the matching upstream stable source tag `v6.18.44` in `/tmp/steamdeck-linux-6.18.44` rather than trying to decompile an optimized kernel module. The distro suffix means this source trace is the matching upstream base; Arch-specific patch differences were not checked against the built module.

In [`amdgpu_discovery.c` at v6.18.44](https://github.com/gregkh/linux/blob/v6.18.44/drivers/gpu/drm/amd/amdgpu/amdgpu_discovery.c), live IP discovery drives block-family selection: this Deck's GC `10.3.1` selects `nv_common_ip_block`, `gmc_v10_0_ip_block`, and `gfx_v10_0_ip_block`; MP0 `11.5.0` selects PSP v11; MP1 `11.5.0` selects the SMU v11 block; and SDMA `5.2.1` selects SDMA v5.2. PSP v11's early setup in [`amdgpu_psp.c`](https://github.com/gregkh/linux/blob/v6.18.44/drivers/gpu/drm/amd/amdgpu/amdgpu_psp.c) explicitly sets `boot_time_tmr = false` for MP0 `11.5.0`, so Linux later provisions the TMR instead of assuming firmware did so at boot. This matches the live log's PSP-loaded DMUB and runtime TMR reservation, but does not provide a safe macOS sequence by itself.

The same source registers common/GMC, interrupt, PSP, SMU, display, GFX, SDMA, and media blocks from discovery results. GC `10.3.1` identifies the Van Gogh family (`FAMILY_VGH`); Display Core then maps that family to DCN `3.01` in [`dc_resource.c`](https://github.com/gregkh/linux/blob/v6.18.44/drivers/gpu/drm/amd/display/dc/core/dc_resource.c) and calls `dcn301_create_resource_pool` in [`dcn301_resource.c`](https://github.com/gregkh/linux/blob/v6.18.44/drivers/gpu/drm/amd/display/dc/resource/dcn301/dcn301_resource.c). That pool marks the device as an APU, enables DMUB, and defines four timing generators, video planes, stream encoders, and DDC engines. The live discovery table independently reports DMU `3.0.1`; the resource-selection code uses the Van Gogh ASIC family to choose DCN301. Connector wiring still depends on this Deck's VBIOS/ACPI and live link state.

The live sysfs discovery directory reports `num_ips = 36`. RedNavi's helper emits 72 rows because it walks both numeric hardware-ID directories and their named aliases; those rows represent 36 separate IP entries. I captured the debugfs discovery blob read-only to `/tmp/van-gogh-amdgpu-discovery.bin`; its allocated blob is 10 KiB, its declared binary size is 1068 bytes, and its IP table is version 2. The Python decoder validates both additive checksums and all table/die/entry bounds, then matches all 36 parsed versions and base arrays against live sysfs. The Kext now reads the same table from the default VRAM TMR through the BAR5 index/data window after PSP IFWI readiness, then applies the same bounds and IP-version checks. The raw capture remains in `/tmp`, not in the repo. In Linux's discovery parser, base-address values are dword offsets and are installed into per-IP/per-instance register-offset tables; they are not PCI BAR physical addresses. The Kext now has a bounded register resolver, but it does not read IP registers or configure hardware yet.

`SOC15_REG_OFFSET` in [`soc15_common.h`](https://github.com/gregkh/linux/blob/v6.18.44/drivers/gpu/drm/amd/amdgpu/soc15_common.h) computes `discovery_base[BASE_IDX] + register_dword`. Linux's [`amdgpu_device_rreg`](https://github.com/gregkh/linux/blob/v6.18.44/drivers/gpu/drm/amd/amdgpu/amdgpu_device.c) treats that result as a dword offset, reads BAR-mapped MMIO when its byte offset is less than `rmmio_size`, and otherwise uses a PCIe register accessor. This is why BAR bounds must be checked after adding the base and register offset, and why an out-of-BAR result cannot be made safe by simply mapping BAR5.

## iGPUTalks comparison

The neighboring `iGPUTalks-main` README claims support for Radeon 660M and 700M-series APUs, but the source currently present here is only an `IOService` probe/start stub. Its `start()` method logs PCI vendor/device/revision and registers the service; it contains no AMD GPU initialization, framebuffer setup, firmware parsing, memory management, or acceleration implementation. Its personality matches AMD display-class PCI devices broadly. The Xcode project compiles only `iGPUTalks.cpp`; the referenced `MacKernelSDK` directory is absent from this checkout, and there is no bundled Lilu integration despite a small unused header referring to it. The README says BSD-3-Clause, but this checkout has no license file.

The 660M is a reasonable architectural comparison: AMD lists it as a six-core Radeon iGPU, while this Deck's Linux driver reports eight active CUs and Van Gogh-specific GFX/SDMA/VCN/DCN blocks. AMD's open ROCm architecture map distinguishes Van Gogh as `gfx1033` from Rembrandt as `gfx1035`, which is the family used for 660M-class Ryzen 6000 APUs. Shared RDNA 2 lineage makes the 660M a useful hardware reference, but support for it would not automatically establish compatibility with Van Gogh's different IP configuration, VBIOS, memory setup, and Steam Deck display wiring. The local iGPUTalks code does not yet demonstrate working support for either GPU.

## Capture limits

- The Linux kernel log confirms that Van Gogh initializes its GPU, memory, video, and display blocks successfully under `amdgpu`.
- `modetest.txt` was captured on the actual Linux host and contains live connector/CRTC/plane data.
- `amdgpu-boot-log.txt` captures the Linux initialization path and its firmware/IP block messages.
- `pci-gpu.txt` captures the PCI configuration and BAR resource ranges.
- On the live Deck, debugfs is mounted and the GPU directory is `/sys/kernel/debug/dri/0000:04:00.0/`. It exposes read-only `state`, `amdgpu_dm_dtn_log`, `amdgpu_dm_dmub_fw_state`, `amdgpu_firmware_info`, and `amdgpu_discovery` entries. The raw `amdgpu_regs*` interfaces are also present, but do not use them for a broad dump until a DCN 3.0.1 active-path register list is prepared.
- In the pasted capture, `amdgpu_dm_dmub_fw_state` returned `Operation not permitted` even from the root shell; `amdgpu_discovery` emitted binary data when read with `cat`. Use the text sysfs `ip_discovery` interface or the existing decoder for discovery data, and don't treat either failed/raw read as a decoded diagnostic.
- The VFCT payload has been copied into this project as `VFCT.bin` and parsed for the display routes summarized above. Keep this firmware dump local unless you intend to share its VBIOS contents.
- The framebuffer sysfs values visible here are not a reliable live KMS mode report, so they are intentionally omitted.

The next useful Linux capture is a carefully scoped register/state snapshot for the active eDP path, to correlate the panel route with the working KMS mode. RedNavi's `linux_collect.py` and `linux_dcn_pipe_dump.py` are not suitable for this: they use a DCN 3.2 register list and their DIG selection assumes Navi 32 wiring. A Van Gogh capture needs the DCN 3.0.1 register definitions and active path from the matching Linux driver. The upstream DCN301 resource file is the starting point for identifying the register groups; the Deck's `modetest.txt` already provides the live mode and connector state. Limit reads to registers the active path has powered; RedNavi's own bring-up notes report that broad reads of gated display blocks can stall a machine. Do not treat Linux DRM plane modifiers as macOS framebuffer settings.

The macOS driver core opens the matched PCI provider and maps BAR5 through IOPCIFamily. It restores PCI memory decoding on failed start or detach if it enabled that bit. It publishes the captured PCI model string and 4096 MiB VRAM total as identification properties, not as hardware initialization or allocation. The driver now waits for the PSP IFWI-ready bit, reads `RCC_CONFIG_MEMSIZE`, and copies the discovery TMR from VRAM through the common BAR5 `MM_INDEX/MM_DATA` window. It saves and restores the index-selector registers around the copy, validates the binary/table checksum and bounds, and verifies the captured GC, SDMA, VCN, MP0, and DMU versions. It also accepts an injected `VanGoghDriver,ip-discovery` blob as an override. The validated table is retained for range-checked per-IP register reads; the only IP registers read are the DCN301 HUBP surface registers described above, and only populated surfaces are read beyond their format register. These reads do not configure GPU state. PSP firmware submission/command transport, protected VRAM allocation/TMR provisioning, SMU, SDMA, GFX, DMUB, and DCN scanout remain unimplemented. The new `VanGoghFramebuffer` service accepts only a parent-published ready flag, a linear CPU-writable surface confirmation, and validated scanout address, byte length, pitch, dimensions, and refresh rate. The current PCI service still does not publish these properties, so the framebuffer personality remains dormant. It refuses to attach unless the parent confirms both a linear CPU-writable scanout and that the DCN 270-degree plane rotation is already programmed; with a 1280x800@60 source surface, it reports an 800x1280@60 panel timing with `kIOScaleRotate270` and exposes `IOFBScalerInfo`. The PCI service publishes the real 128-byte EDID captured from `/sys/class/drm/card1-eDP-1/edid`; the framebuffer validates the header and checksum before exposing it and serving DDC block requests. It does not perform AUX/DDC reads. The parent must still initialize the panel path and program DCN plane rotation for scanout; there is no backlight control. The live debugfs capture reports SMC firmware `63.15.0`, ASD `0x21000115`, TOC `1`, and DMUB `0x03000010`. The live 1068-byte discovery binary in `/tmp/van-gogh-amdgpu-discovery.bin` was parsed on Linux and all 36 die-0 entries matched `/sys/bus/pci/devices/0000:04:00.0/ip_discovery`. Do not treat BAR0's 256 MiB aperture as if it directly spans the Deck's 4 GiB memory. `tools/linux_ip_inventory.py` reads the kernel's exported table and checks its 36 numeric entries against `num_ips`. `tools/linux_resolve_ip_register.py` calculates direct BAR5 candidates from an explicitly supplied base index and register dword offset, then bounds-checks the entire 4-byte access. On this host it resolves GC HWID 11, base index 0, register `0xDA4` to BAR5 offset `0x8010`, and MP0 HWID 255, base index 0, register `0x61` to BAR5 offset `0x58184`; these are calculations only, with no MMIO read. The caller remains responsible for selecting the matching Van Gogh register header and access path for each IP version.
